# Vclarity architecture

Vclarity uses WXT (Vite) for a Manifest V3 Chrome 116+ extension, a React native side panel, a bounded on-demand isolated-world script, and a Hono Node service. `packages/shared` owns strict Zod schemas and the explicit workflow. No application UI is mounted in third-party documents.

The worker persists only lightweight per-tab reports in `chrome.storage.session`. Every selection gets a new session UUID; every AI call gets a request UUID. Late messages must match both. Per-tab operations are serialized. Navigation and tab changes cancel work. Each panel binds to its own Chrome window, so broadcasts for other windows are ignored. Ports reconnect after worker suspension, and screenshot delivery requires a current panel acknowledgment rather than trusting an in-memory connection count. The panel owns ephemeral screenshot memory, local image workers, and abortable requests; closing it destroys screenshot memory. Worker suspension does not lose reports, but an interrupted capture requires recapture.

Only the background worker invokes `captureVisibleTab`, verifies the active tab before and after capture and after acquiring the capture lock, and validates viewport stability. A short-lived content watcher also rejects nested-container scrolling during capture. The image pipeline derives bitmap coordinates from actual bitmap/viewport ratios, without equating emulated DPR to captured bitmap scale. Screenshots and credentials are never written to report storage. Provider credentials remain server-side. An explicit Settings save stores only the separate local API access token in `chrome.storage.local`, restricted to trusted extension contexts; this is ordinary local storage, not an encrypted vault. The settings clear action removes it. Screenshot memory remains ephemeral, and AI transport requires an explicit button after preview and disclosure.

The authenticated `GET /connection` route returns a shared validated configuration summary without provider calls, screenshots or analysis rate-budget consumption. It confirms the local token and reports provider/model/key configuration; image support is unknown except for known unsupported Ollama GPT-OSS models. It cannot establish external provider authentication or quota. The unauthenticated `/health` route remains a smaller service-liveness check.

Security order: validate context and message → verify session → verify state transition → perform privileged operation. Content messages are accepted only from the top frame of the current tab; panel messages only from this extension's sidepanel URL. The API binds to loopback by default, requires an access token, validates image headers, bounds bodies and output, and rate limits. Website text and screenshots are untrusted model input. Optional DOM context is omitted in phase 1 to minimize data collection.

Implementation proceeds through shared contracts and extension foundation, fixture-backed DOM measurement, capture and pixel processing, provider integration, sidebar and Markdown serialization, then static/unit/browser checks. The README and verification log record actual commands and remaining environment limits.
